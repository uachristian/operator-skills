# Recent build/install reconciliation

## Purpose
Answer whether recently completed work actually reached its intended runtime, without treating every prototype or old roadmap as overdue deployment.

## Bounded discovery
1. State a recent window and explicit exclusions. Include older candidates only when current evidence makes them relevant.
2. Discover from current vault release/closeout titles, non-Git build folders, profile-local scripts/plugins, deployment manifests and active scheduler/supervisor metadata. Use conversation history secondarily to resolve exact owner approval or stop points.
3. Exclude sensitive personal content. Deployment/code/model metadata usually suffices.
4. Deduplicate worktrees, candidate generations and overlapping release manifests. Record candidate rows separately from unique products.
5. Divide independent domains among bounded read-only workers when useful. Give each a source scope, evidence output path, mutation prohibitions and a cutoff; parent verifies decisive external-state claims.

## Per-candidate evidence
Record:
- expected deliverable and canonical source identity;
- completed review/test evidence and its exact scope;
- intended live targets and installed byte/hash parity;
- owning runtime, startup identity or deployment receipt;
- current relevant job result, natural execution evidence or physical/UAT boundary;
- explicit approval hold, superseding release or concurrent-work owner;
- classification, confidence, unresolved evidence and one next action.

A note saying “not installed” is only a discovery lead. Look for later receipts. Conversely, “deployed verified” may be historically true while today's cron is blocked.

## False-positive controls
- Old manifest mismatches: compare to the newest approved owner of each file, not every historical manifest simultaneously.
- Concurrent installs: timestamp observations and reread decisive targets before finalizing. Report incomplete closeout to the session already handling it rather than competing with it.
- Runtime identity: an older startup SHA is not a loaded-module attestation. Do not infer a vulnerable dependency in memory from it alone.
- Device acceptance: stored/readback-verified Home configuration is installed even when phone rendering or owner-watched physical behavior remains unverified.
- Experiments: a completed experiment recommending unchanged defaults creates no install obligation.
- Technical review: APPROVE-CANDIDATE does not authorize live installation, public release, permission expansion or business actions.

## Source-authority failure branch
A whole-file adapter pin can block both read-only PO eligibility and mutation consumers after otherwise approved shared changes. Read the precise loader/verifier error. Do not classify every nonzero exit as the same root cause until logs establish it.

If repair is authorized:
1. Recover the exact pinned baseline bytes; Git HEAD may omit already-approved working-tree changes. Validate any recovered backup against the original full hash.
2. Compare actual old/current adapter contracts and preserve approved live improvements when reconciling their source mirrors.
3. Stage one exact candidate. Keep hash, path, permission, scope, retry and approval checks intact.
4. Disclose that making the verifier pass may resume already-enabled autonomous consumers. That is production activation, not harmless metadata cleanup.
5. Follow the domain's reviewed install and rollback gates. Never restore transaction/claim ledgers as part of source rollback.

## Closeout
Separate installed-source proof from runtime and workflow proof. A one-shot read-only observation of normal scheduled results can establish recovery without a forced business test write. Keep it bounded, with a completion notification and explicit timeout/failure result; do not add a recurring monitoring service by default. Require genuinely post-activation completed-run evidence, not an old success paired with a new start timestamp.

Report installed/active, deliberately held, installed-but-blocked and unknown items separately. If audit artifacts were written, say operational files/services were unchanged and audit notes were created—not “files modified: none.”
