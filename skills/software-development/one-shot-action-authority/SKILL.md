# One-shot Action Authority

## When to use

Use this skill when reviewing, designing, or remediating action cards, approval buttons, Telegram inline keyboards, callback data, webhook acknowledgements, owner-run elevated installers, or any transport-delivered UI that lets a human authorize an irreversible, owner-gated, customer-facing, financial, HR, system, or production mutation.

For non-technical owner-operated changes, make the human interface part of the initial acceptance criteria: one clearly named launcher, one visible zero-mutation preview, one exact plain-language decision, visible completion evidence, and technical verification handed back to the agent. Do not wait for owner confusion before replacing a manual multi-command procedure.

- Separate business approval from local tool/runtime approval, requires the UI plan to be derived from the digest-approved machine-readable manifest, requires React input values to survive a settling interval plus rendered review before Save, uses UUID-backed metadata and count-only empty-field receipts, treats Save timeouts as applied-response-ambiguous rather than retryable, and gates rollback on exact metadata identity, zero values, zero dependencies, and fresh owner authority. For fields whose UI omits nullability/default controls, it also covers live mutation-input introspection, provider-specific default canonicalization, visible-UI option creation followed by a minimal UUID-bound constraint update, conditional rollback, and bounded capture-restart authority.
- Cover proposal-versus-execution bundle binding, descriptor-loaded bootstraps, isolated Python startup, honest owner-session trust boundaries, permanent one-shot claims, ambiguous-create handling, create-only fallback when rollback proof is incomplete, CRM-style relation dependency coverage, strict readback types, and credential-free release probes.

## Durable owner decisions and review annotations

Treat review-only confirmations as durable decisions even when they cannot mutate the underlying business record. Trace the existing authenticated owner UI through exact-card rendering, persisted consumption and the normal readback surface before calling the feature integrated; a signed standalone prototype does not finish that workflow.

Integrate in this order: locate the actual deployed callback facade and configured owner-policy reader; render exact source anchors and current revision in the existing owner UI; arm confirmation only after an exact original-message edit receipt; transactionally consume the confirmation and persist the result; then exercise the normal digest/readback consumer after restart. Search current source for the required symbol before assuming historical host paths still apply. Extend both UI callback allowlists and cross-store card replacement/revocation, because a button can otherwise be silently filtered or leave superseded authority active. Treat callback data as a selector only, and keep authenticated actor/chat/message coordinates out of model-controlled arguments.

Prefer a disjoint review sidecar when existing obligations must remain authoritative. Persist exact IDs, revision digests and authenticated decisions rather than raw message bodies; reconstruct source excerpts transiently for owner review. Verify that confirm, deny, revoke and rollback preserve every original obligation and later manual disposition. Rollback must disable/archive the new authority store without restoring stale legacy-state snapshots. Distinguish successful source installation and gateway reconnection from the owner's actual normal-layout walkthrough; name the remaining owner action rather than simulating it.

Test the ordering of committed decisions independently from card issuance and expiry. Reproduce confirm→deny, deny→confirm, revocation, equal-clock decisions and cards decided out of issuance order through the actual callback→store→renderer path. Never select the latest owner choice using card creation time, coarse wall-clock timestamps or unordered database enumeration: those can display a superseded decision. For SQLite-backed decisions, allocate a monotonic sequence under the same `BEGIN IMMEDIATE` transaction that consumes authority and writes the authenticated decision; bind the sequence into the authenticated payload. Read relevant decisions in one snapshot and select the highest valid committed sequence. Reject missing, invalid or duplicate relevant sequences instead of inventing an order for legacy receipts. Exercise transaction rollback, restart, concurrent distinct-card decisions and old-receipt revocation followed by a newer confirmation before claiming the ordering fix verified.

Keep authenticated decision receipts distinct from source identity and source freshness. A profile-path namespace is not provider-account attestation, and repeated native reads are not an atomic external snapshot. State those residuals explicitly and keep uncertain linkage review-only rather than using it to clear obligations.

## Approval-evidence repairs and staged integration

When the owner asks to restore an action "as it used to work", first find why it stopped: diff the handler against older backups (backup directories, `*.bak-*`) and search the vault for the repair note. If it was deliberately blocked for missing owner binding, do not revert to the old direct-from-model-text write; offer the owner a choice between the legacy behavior and an owner-bound tap-to-confirm card built on the profile's existing proven card pattern , recommending the card. Also verify the backend dependency still exists and the last successful audit entry before promising a fix, and separate install, OS permission grant (owner-physical), code change, flag enable and restart into distinct approval steps.

Before treating missing approval metadata as a logging bug, trace the authenticated owner event through scope binding, one-shot consumption, transport and audit. Request IDs and caller-filled approval labels are not business authorization.

Before building a synthetic approval lab, inspect the existing handler and the real endpoint's required semantics so the demo does not model an unavailable integration. Keep staged approval, fixture identity, and modeled concurrency guarantees distinct from live authority; do not present a working prototype as a repaired production write path.

## Core rule

Once an actionable callback/button may have been committed to an external provider, every ambiguous outcome is **applied-response-ambiguous**. The system may preserve audit evidence and clear local continuation state, but it must not retry, redeliver, fall back, auto-continue, or restart-recover that callback authority into a different provider message.

Prefer a missing button/manual reconciliation over duplicated authority.

For one-shot schema/API mutations, apply the same rule at the action boundary, not only messaging callbacks:

- Treat a bare `Go`, `Approved`, or equivalent as authority only for the exact candidate most recently presented as execution-ready. If the latest handoff says the candidate is pending review, non-approvable, preparation-only, or explicitly held, the same reply may continue preparation/review at most; it cannot authorize provider mutation. Present fresh final bytes and their complete physical effects after all required review gates before asking for execution authority.
- Account for provider-managed consequences separately from explicit API calls. A create/promote operation may implicitly assign aliases, publish generated hostnames, create reciprocal metadata, or alter another provider-managed surface without a second endpoint call. Manifests, claims, receipts, review prompts, and owner handoffs must declare both the explicit transport-call budget and every expected indirect physical effect; “zero alias/domain/etc. API calls” must never be summarized as “zero alias/domain/etc. changes.” Bind and read back the indirect surface independently.
- Atomically create and fsync a permanent action claim before mutation transport. Any existing attempted, uncertain, applied, or rolled-back claim permits readback-only reconciliation and zero additional mutation deliveries.
- Hold one exclusive cross-process mutation lease from the fresh baseline through transport, authoritative readback, and any conditional rollback.
- A post-baseline UUID delta does not prove ownership after an ambiguous create. Automatic rollback requires an exact source UUID returned by that mutation; otherwise preserve state and enter manual hold.
- Persist `rollback_delivery_attempted_readback_required` before delete. Catch every delete response loss, reconcile authoritatively, and never retry the delete.
- Bind approval to a frozen execution manifest covering the proposal, standalone implementation, launcher, interpreter, native executable image where distinct, and non-system transport executables. The launcher must hash each file once and execute the same captured implementation bytes; mutable helper imports or PATH-resolved executables sit outside the approval boundary. For Python launchers, `__file__`, `sys.argv`, and `sys.executable` are defense-in-depth signals—not an immutable entrypoint proof. On macOS, require the exact kernel-observed startup vector from `sysctl(KERN_PROCARGS2)`, bind its canonical digest, repeat the check in the runner before secret access, and regression-test forged in-process relocation.
- Treat local bindings as expectations, never provider evidence. For publish/install workflows, read back the provider-stored package bytes or an equally strong provider-observed digest, pin install to the exact approved version when supported, and parse convergence summaries strictly rather than copying bound hashes or hardcoding unparsed counters. The authority-owning command must run provider collection internally; caller-supplied snapshot JSON is evidence only and can never advance baseline/readback state. Bind the claim digest to one canonical state root, capture and upload verified bytes rather than a mutable path, and recover surviving receipts as readback-only authority. For post-install convergence, bind plan generation to the exact application root **from process startup**: if the SDK captures cwd-derived build/checksum state during import, use a fixed no-shell child `plan` command with exact app-root cwd rather than runtime `chdir()`.
- Prove authenticated provider readback immediately before minting a business-mutation claim. For credential-creating or privilege-sensitive endpoints, also prove that the current credential is the exact token class accepted by the lowest mutator; successful reads and a generic `OAuth valid` check are insufficient because application/playground tokens may read metadata while a server guard requires a user-session access token. Inspect only non-secret claims or use a no-write capability probe—never print the token. If a browser user session is required, keep its transport and secret handoff separately bounded and do not approve execution until the token can reach its final private file without screenshots, clipboard sync, browser persistence, argv, environment variables, or logs. If credential acquisition is strictly read-only, an auth/readback precheck failure may leave business authority unconsumed. If OAuth refresh, browser-session renewal, local credential rotation, or another owner-visible credential effect is authorized before the business baseline, first create and fsync a permanent no-overwrite **preparation-attempt** record; that record consumes the approval even when the later baseline or business claim fails. Keep the later business-mutation claim separate and create it only after both intended principals reproduce the exact baseline. After any consumed preparation/claim/receipt artifact, failure permits readback-only reconciliation and never authorizes credential renewal or mutation redelivery. When an exact mutation fails, journal a sanitized provider error class/code sufficient for diagnosis without retaining secrets or customer data; collapsing all GraphQL `errors` into `provider_envelope_invalid` can consume authority while destroying the root-cause evidence.
- If authority is persisted in more than one durable artifact (for example a primary claim plus an independently fsynced receipt), **any surviving artifact is consumed-authority evidence**. Precheck and apply must check every durable authority record, not only the primary claim. Isolated claim loss while a receipt survives must produce readback-only reconciliation and zero additional provider calls; add a regression probe for that partial-state loss.
- For provider workflow-step creation, never treat a returned UUID, expected step count, or correct parent/child wiring as semantic success. Before journaling `<operation>_succeeded` or dispatching the next mutation, read back and exact-check the step's object/action target, complete field map, `valid` boolean, retry/error policy, schemas, and unchanged sibling graph. Provider validation with zero errors is insufficient when unexpected warnings expose an empty/default step.
- Dependency blockers must gate both success and rollback. Enumerate provider metadata dependencies (views, roles, fields) across every authoritative object, not only the source and target objects; recursively inspect JSON-valued filters and other nested metadata. After rollback, prove the complete pre-baseline UUID set and every provider-managed lifecycle reference are restored/removed, not only the primary field pair. If the provider's dependency graph cannot be enumerated authoritatively, remove automatic rollback from the candidate: preserve malformed/ambiguous state for a separately reviewed and separately approved rollback instead of guessing that delete is safe.
- Require two distinct provider-valid IDs for reciprocal creations, exact UUID-list uniqueness, and count/list/set arithmetic that cannot hide duplicate IDs. Validate source and reciprocal primitive types independently; do not assume reciprocal provider defaults match the source.
- For provider-managed reciprocal relations, validate every selected nested binding in both field-oriented directions—not only top-level object IDs and reciprocal UUIDs. Exact-check relation type; source/target object ID, API name, and label; and source/target field ID, owning object ID, API name, label, and type. Corrupt each nested property independently in credential-free probes and require direct postcheck failure plus end-to-end manual hold with zero rollback.
- A create-only claim must hold at the lowest transport boundary, not only by source-code reachability. Generic read helpers reject all mutations, and the sole mutation wrapper allowlists the exact create operation plus canonical variables. Do not classify GraphQL by `lstrip().split()[0]`: valid ignored tokens such as BOM, commas, whitespace, and leading `#` comments can hide a mutation. Either structurally parse the document or skip the complete ignored-token prefix and permit only an explicit `query`; probe plain, commented, CRLF, BOM/comma-prefixed, fragment-prefixed delete shapes for rejection before network/UI transport, with commented-read and exact-create positive controls.
- For metadata/schema canaries that claim no baseline drift, digest the complete selected metadata surface, not a convenience subset. If the readback query selects object plural names, labels, icons, or booleans, include them in the baseline digest and check booleans with strict `type(value) is bool`; numeric `0`/`1` must not pass. Poison these selected object fields in credential-free probes and require both direct postcheck and fake-transport executor to refuse success.
- Provider canonicalization authority is field-specific. Never implement an approved timestamp exception through a suffix/type heuristic such as `key.endswith("At")`; use the exact manifest-bound field allowlist, require exact equality for adjacent fields, and replay negative controls before allowing the mutation tail to continue.
- A successor target set must equal the immediate predecessor's unattempted tail while also excluding every transitively ancestor-consumed target. Full semantic reconstruction may resurrect already-created records that the immediate predecessor no longer lists; bind a fresh destination baseline, prove every exclusion, require zero unexplained additions/removals, and mint new action IDs without changing targets. Successor launchers must compare actual mapped/new counts to the current manifest and predecessor tail; never preserve a historical fixed new-action cardinality after source growth or evidence refresh.
- Post-mutation browser UAT that gates completion is part of one-shot authority. Bundle and archive the exact UAT producer plus every semantic dependency such as hosted field/option metadata; bind the exact bundle, release, claim, receipt, destination-after, contract, producer, and verifier; and require the final verifier to execute that exact producer's stored-sample verification plus a fresh authenticated live browser verification. Raw text/DOM hashes and other SHA-shaped scope fields are not evidence of origin. Persist a privacy-safe canonical semantic receipt derived from trusted field identity, metadata-derived label digest, destination-derived expected-value-set digest/count, and matched count; recompute it during stored verification and require the fresh live semantic receipt set to equal the persisted sample set. A disposable closeout verifier must stage the complete reviewed dependency closure across fixed checkout and private-state roots, never fall back to live state, and remap only canonical bundle-role paths to identical staged bytes with hash/size/mode checks.

Prefer a missing button/manual reconciliation over duplicated authority.

## Required design shape

1. **Bind immutable authority before rendering.** Callback data must bind one immutable request and exact authoritative provider coordinates where applicable.
2. **Detect callback authority at the final transport boundary.** Do not rely only on upstream producers or prompt text.
3. **Reject unbound confirmation flags.** A caller-supplied boolean such as `callback_ledger_confirmed=true` is not proof of persistence. Confirmation must be created at the final boundary or verifier-bound to the obligation ID, session, provider coordinates, callback/content digest, and terminal ledger state for this exact mutation.
4. **Create a durable non-redeliverable record before provider await.** Callback-bearing sends need a terminal or otherwise non-recoverable ledger state before the provider call can commit.
5. **Make the initial insert safe and monotonic.** Avoid `pending -> terminal` windows for callback authority; if the row is created, it should already be non-redeliverable. Never use replacement/upsert behavior that can reset a consumed terminal row back to a dispatchable state.
6. **Separate preparation from one-shot consumption.** Use a terminal prepared state (for example, `callback_prepared`) that ordinary recovery never redelivers. At the final adapter boundary, atomically compare-and-swap that exact row to the provider-ambiguous terminal state immediately before dispatch. Require the prepared state in the compare-and-swap so copied proof, replay, and concurrent callers yield at most one provider mutation.
7. **Guard terminal transitions.** A prepared callback row must not become `delivered` or ordinary `failed` unless the final adapter successfully consumed it first. Generic producer result handling must not bypass the adapter gate.
8. **Fail closed if mandatory recording or consumption fails.** If the callback row cannot be inserted, exactly matched, or atomically consumed, suppress the callback-bearing provider call and surface a terminal non-retryable error for human reconciliation.
9. **Classify ambiguous provider outcomes before generic retry heuristics.** Provider `NetworkError`, timeout, remote-close, wrapper text, flood text, or too-long text after callback dispatch must not authorize retry or fallback.
10. **Preserve terminal semantics through wrappers.** Shared delivery results must remain unsuccessful, non-retryable, non-overflow, and non-fallbackable. An edit-then-send wrapper must propagate callback-ledger failure or ambiguity as terminal rather than converting it into a fresh send.
11. **Separate ordinary delivery recovery.** Non-callback text can remain at-least-once with honest recovered markers; do not weaken ordinary recovery unless it carries action authority.
12. **Make restart recovery authority-aware.** Startup sweep may claim terminal prepared/ambiguous rows only to clear local resume/continuation flags, never to call the provider.
13. **Run security cleanup independently.** Callback cleanup must run even when ordinary redelivery is disabled and when the provider adapter is unavailable.
14. **Fail closed on resume cleanup.** If clearing resume state fails, block that session from auto-resume for the process; if terminal-ledger recovery fails, block affected-platform auto-resume.
15. **Handle legacy rows.** If an older build left failed/attempting/pending rows that contain callback markup, terminalize and clear resume instead of redelivering.
16. **Cancel queued workers before terminal cleanup.** A startup timeout must atomically cancel a pending future, or retain cleanup ownership until a running worker acknowledges cancellation and unwinds. `shutdown(wait=False)` is not cancellation; never release credentials, unregister authority, or close child resources while delayed work remains runnable.
17. **Bind release claims to completed evidence.** Package manifests, owner context, and handoff instructions must not claim `APPROVE` from a hard-coded label, expected future result, or review of different bytes. Verify a completed exact-commit/tree review artifact before packaging or keep the release explicitly pending.
18. **Eliminate persistent enabled-gate crash windows.** For owner-session operators, prefer a signed gate that remains byte-for-byte disabled plus an ephemeral 32-byte-or-stronger dispatch capability whose digest is authority-bound. Keep the raw capability memory-only, verify it before durable consumption, consume before transport, and let process death destroy the only pre-consumption capability. If a temporary enabled gate is unavoidable, bind and close it atomically under the same cross-process lock; `finally` is defense in depth only.

## Verification checklist

- [ ] Ambiguous callback delivery produces exactly one provider call.
- [ ] Every callback-bearing adapter entry point proves a matching terminal ledger record; copied or caller-supplied confirmation booleans cannot authorize a provider mutation.
- [ ] A prepared proof is consumed atomically exactly once; sequential replay and concurrent double-submit produce at most one provider call.
- [ ] Re-preparing the same obligation cannot reset `ambiguous` or `delivered` back to a dispatchable state.
- [ ] Wrong session, platform, chat/thread, content, provider message target, mutation reference, or obligation ID yields zero provider calls.
- [ ] The final adapter verifier derives/checks the actual provider operation kind and coordinates it is about to dispatch; proof for a send cannot authorize an edit, and proof for edit target A cannot dispatch to target B.
- [ ] Dead-owner `callback_prepared` cleanup makes the row non-consumable (for example by terminalizing to `ambiguous`) before or while clearing resume; claiming/restamping a prepared row is not sufficient.
- [ ] Generic `mark_delivered`/`mark_failed` handling cannot move an unconsumed prepared callback row out of its terminal non-redeliverable state.
- [ ] No keyboard-bearing retry occurs for provider errors, wrapper errors, or exception text variants.
- [ ] Shared wrapper result is `success=false`, `retryable=false`, non-overflow, and does not enter fallback transport; edit rejection cannot fall through to a fresh keyboard send.
- [ ] Crash before/inside provider await leaves a non-redeliverable row.
- [ ] When the persistent gate remains disabled, hard exit after authority persistence but before consumption leaves no usable authority because the raw authority-bound dispatch capability was memory-only and is gone; wrong/lost capabilities produce zero provider calls.
- [ ] The raw dispatch capability never appears in argv, environment variables, files, receipts, logs, exceptions, queued jobs, or operator output; sequential and concurrent reuse still produce at most one provider call.
- [ ] Failure to create the terminal ledger suppresses the callback send.
- [ ] Restart sweep of terminal ambiguous rows clears resume/continuation state and makes zero provider calls.
- [ ] Callback cleanup still runs with ordinary redelivery disabled and with the provider adapter unavailable.
- [ ] Resume-clear failure blocks that session from model auto-continuation; terminal-ledger recovery failure blocks affected-platform auto-resume.
- [ ] Restart sweep of legacy recoverable callback-markup rows terminalizes them and makes zero provider calls.
- [ ] Positive controls prove ordinary non-callback delivery recovery still works.
- [ ] Exact artifact review includes startup/restart probes, not only live-send probes.
- [ ] An owner-run Windows package executes release-critical process-local logic under the exact launcher runtime (especially Windows PowerShell 5.1), with host mutations mocked; parsing or testing under newer `pwsh` is not accepted as runtime proof.
- [ ] Firewall conflict checks classify application/service/package/address/interface/policy filters, preserve all pre-existing rules, and prove authorization independently at the service/key/forced-command layer instead of treating `LocalPort: Any` as a removable unrestricted rule.
- [ ] A non-technical owner can complete an owner-run privileged path without assembling commands, supplying secrets, or interpreting source code; the dry run and explicit activation decision remain visible.
- [ ] The external trust root and residual local-tamper boundary are stated explicitly; usability does not silently broaden authority.
- [ ] Every review label in a package or handoff is derived from a completed review of the exact commit/tree and bytes, not a constant, predecessor verdict, or pending asynchronous job.
- [ ] Private release artifacts are created directly at the final path with no-overwrite semantics and verified mode `0600`; copy-then-rewrite mode inheritance is covered by a negative regression.
- [ ] The approvable binding was regenerated in its final durable canonical state root, the exact-commit worktree is durable and clean, and every temporary binding/packet was retired so only one digest can be approved.
- [ ] Immediately before claim creation, authenticated provider readback succeeds against the bound remote and reproduces the exact baseline. Expired access tokens are refreshed only through the provider SDK's supported path using an already configured refresh credential; no token value or signed readback URL enters output. Auth/readback failure before claim creation leaves authority unconsumed, while failure after a consumed receipt permits readback-only reconciliation and zero mutation retries.
- [ ] If an overlapping session was stopped, stable bytes/status were verified after the stop and any late commit was reviewed as untrusted evidence before transplant into the isolated final worktree.
- [ ] A queued worker cannot start after its owner returns timeout; pending futures are cancelled, running-worker races are acknowledged, and child credentials/resources remain owned until unwind completes.
- [ ] After successful activation, the immutable archive matches every committed Git blob, the confirmed-private remote default-branch SHA equals the local commit, exact-head CI passes, recovery artifacts remain intact, and canonical documentation no longer contains contradictory pre-release state.

## Pitfalls

- Provider-level retry suppression is insufficient if a shared wrapper can still mark the result retryable or too-long.
- A successful fail-closed edit guard is insufficient if its caller treats the result as an ordinary edit failure and falls through to a fresh send.
- A metadata boolean is not durable evidence and is not immutable request binding; verify a structured confirmation against the exact ledger row and provider mutation.
- Do not trust an opaque mutation reference alone. At the final adapter method, parse or independently bind the current provider operation kind and exact coordinate fields being dispatched (especially edit message IDs).
- Bind the bot/provider principal as well as owner, chat and message. Checking only that the message sender equals the currently authenticated bot does not reject a copied token/body under a different bot with matching private-chat/message coordinates. Require the released bot identity and persist it in the exact card binding; keep a cross-bot collision regression.
- A process-local grant must bind the complete consumed card/receipt, not only action ID and digest. If durable card evidence disappears before the worker starts, reject the surviving in-memory grant rather than relaxing to proposal-only checks. Initial inert button output also needs nonempty visible text; a parser-only test can otherwise pass while the real provider refuses an empty message.
- Verifying an already-ambiguous row is not one-shot authorization: the same proof may be replayed. Require an atomic prepared-to-ambiguous compare-and-swap at the final adapter boundary.
- Claiming a dead-owner `callback_prepared` row during startup cleanup is not enough; if the row remains prepared, the stale proof can still be consumed after recovery. Cleanup must make prepared authority non-consumable.
- `INSERT OR REPLACE`/upsert can silently resurrect consumed authority by resetting a terminal row to prepared. For callback obligations, insert once and leave existing rows unchanged.
- Producer tests that replace the real adapter with a mock can accidentally bypass the consume boundary. Assert `callback_prepared` at adapter entry, and separately exercise the real adapter for the atomic consume and provider-call count.
- Generic success/failure bookkeeping must be state-aware; otherwise a mock or alternate adapter can mark an unconsumed prepared callback row delivered or recoverable.
- A terminal state written after provider dispatch does not cover process death during the await.
- A signed disabled gate does not make an abandoned prepared authority safe by itself if a later launcher can still consume it. Either durably consume/terminalize before any crash window or bind an unpersisted high-entropy dispatch capability into the authority so process death destroys the only remaining pre-consumption execution proof.
- Persisting that raw dispatch capability in argv, environment, logs, receipts, queues, or recoverable subprocess metadata silently recreates the replay path the design was meant to remove.
- A two-step checkpoint can leave a replayable pending row if the second write fails.
- Clearing the delivery ledger alone is insufficient when a separate `resume_pending` flag can regenerate the action card.
- Treating `shutdown(wait=False)` as cancellation lets queued work run after terminal timeout and race owner cleanup. Probe delayed thread start deterministically, and check cancellation before credentials, registries, databases, or clients are released.
- Aggregate pass counts do not override one reproducible authority-relocation path.
- Do not treat a reviewed predecessor approval as covering a successor after any source, lockfile, archive, manifest, or release-pin change.
- `git archive` can omit tracked `export-ignore` paths. For full-tree release evidence, package an exact detached checkout's `git ls-files` set and replay with forced staging before comparing `git write-tree`. When verifying an extracted worktree with a fresh temporary index, use `git add -f -A`; without `-f`, tracked files matching `.gitignore` are omitted. Recompute the tree after tests because custom harness files may appear even when pytest's cache provider and bytecode writes are disabled.
- `git fsck --full` does not prove a staged candidate is intact: it may pass the reachable commit graph while the index references missing blobs. Before freezing staged bytes, batch every `git ls-files -s` object through `git cat-file --batch-check`, require all entries to resolve as blobs, and require `git write-tree` plus cached/worktree diff checks. If recovery is authorized, reconstruct only from immutable exact evidence, verify the Git blob ID matches the missing OID before `git hash-object -w`, and never restage mutable worktree bytes as a substitute; then rerun the full graph and index checks.
