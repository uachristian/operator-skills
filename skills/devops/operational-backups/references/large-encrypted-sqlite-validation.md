# Large encrypted SQLite snapshot validation

Use for an explicitly authorized repair-grade backup when random reads through an encrypted image make a full integrity scan impractically slow. Do not skip the required integrity or restore gates.

1. Separate source read speed, encrypted sequential speed, and small/random read speed. Sample the owned verifier and retain only stack symbols/counters; a long `pread` wait is not a Keychain error or corruption verdict.
2. Bind the already completed snapshot to a retained descriptor, expected full-file hash/size and source identity. Never reclassify a timed-out worker as successful without independent artifact verification. Preserve its original failure record.
3. Avoid Python `Connection.deserialize` for snapshots beyond the linked SQLite allocator limit: it may attempt a second whole-file allocation. A caller-owned full-file `mmap.ACCESS_COPY` can be passed directly to the public C `sqlite3_deserialize` API with 64-bit lengths and READONLY alone (4). Do not set FREEONCLOSE or RESIZEABLE on an mmap-owned buffer.
4. Hash original bytes sequentially. If random page faults remain expensive, materialize private COW pages with same-byte writes during that pass; this uses approximately one snapshot's worth of private RAM, not zero physical copying. Apply a memory budget and an external process deadline. Do not create an application plaintext disk copy.
5. Normalize WAL header bytes18/19 to1 only in the private RAM buffer, as documented at https://www.sqlite.org/c3ref/deserialize.html. Never change the source file, map a live uncheckpointed WAL database as a complete snapshot, or discard WAL to make validation work.
6. Keep the map, buffer anchor and progress callback alive until every statement is finalized and synchronous sqlite3_close succeeds. Use explicit C ABI argument/result types. On an unexpected busy close, do not release an in-use buffer.
7. Query only fixed schema-digest and full integrity-check statements; emit counts, hashes, versions and status, never private rows or SQLite error text. Test healthy input, READONLY rejection, private header normalization/source preservation, corruption, malformed headers and deadline interruption.
8. Check actual library identities. Python's sqlite3 module and ctypes.CDLL(None)/system libsqlite3 can resolve different SQLite versions in one process. Never pass a connection pointer between them. An independent reader is useful evidence but is not production-runtime parity.
9. Reopen the actual encrypted artifact and verify decrypted bytes and structural integrity before finalizing its authenticated receipt. For a mutable rehearsal clone, close/checkpoint its writer before validating the main file; keep the original authenticated backup untouched.
